## 背景

用户反馈保存的平安银行日线分析 App 没有实际代码与 Skill 调用逻辑，子 agent 生成的绘图代码未成为 App 的组成部分。当前 recipe 保存目标、约束和能力引用，固定 pipeline 只能串联 Tool 并在末尾解释；现有两类应用不能表达本次确认的完整实现复用。

## 已确认选择

- Tool 保存明确实现与输入输出契约，可含多个固定步骤及固定模型调用流程。Skill 沿用 Agent Skills 标准，可带脚本、参考资料和工具使用说明；平台绑定、验证与启用独立维护。
- 新 App 使用统一步骤模型，组合 Tool、Skill 和内嵌代码，保存输入输出连接及完整本地组件快照。普通运行不改变编排或固定代码；Skill 仅在本节点任务和交付要求内动态执行。
- Creator 基于真实执行证据整理草稿，保留最终交付依赖的成功步骤，区分原执行源码与新改代码。临时代码可直接随 App 保存，不要求先建立独立 Tool。
- 输入变量覆盖提示、代码、调用及数据连接；用户审阅可变输入与固定规则。编辑预览变化并形成新版本，默认只改变 App 内副本。
- 草稿保存、效果验证、正式启用与发布分别处理；验证覆盖原预期与至少一个不同输入的适用用例。平台检查实际结果，Creator 不能宣布验证通过。
- 首版顺序执行，可引用并合并前序结果；支持检查点、有限纠错和可核实结果的中断继续。重新运行重新取数，页面观察不驱动执行。App 层面的分支、循环、并行、嵌套不在首版。
- 旧 App 与原任务保留，按真实记录生成升级草稿，缺口显式展示。标准 Skill 完整可迁移，资产包不默认携带凭据、真实上传和运行历史，接收者重新配置、验证及启用。

## 讨论过的边界

只保存目标模板无法满足检查和复用实际实现的需求；强制所有临时代码先成为个人 Tool 增加不必要步骤。把完整尝试轨迹直接当作执行流程会保留失败和无用步骤。为 Skill 定义平台专用格式会损失通用内容和资源。本轮分别采用完整实现沉淀、App 内嵌代码、最终成功依赖流程和标准 Skill 内容与平台适配分离。
