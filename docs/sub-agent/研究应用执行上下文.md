问题：研究应用的目标可能包含“应用”“运行”等词，单靠拼接提示仍可能被主agent再次分流到创建/保存应用，形成运行→再次创建的循环。

方案：evolution运行入口在完成参数、所有权、能力和本轮文件授权检查后，以 `submit(..., execution_context={kind:'recipe',recipeId,name})` 传入仅服务端可设置的上下文。HTTP消息正文不能设置此上下文，它不授予工具、网络、文件或临时代码权限。上下文存于run.executionContext，绑定幂等摘要，恢复任务时保留。

主agent规划和子任务观察可见该上下文，明确这是已经点击运行的研究目标。正常流程仍选择解释、回答、直接操作、委派或必要澄清；若模型仍返回application或explicitApplication，协调器拒绝交给应用模块，写入具体纠错观察并重新规划，最多沿用全任务3次纠错预算。耗尽后明确失败，不创建另一个应用。

验收：研究应用首次错误返回application后纠正并成功执行；持续错误到预算耗尽失败且从未dispatch；HTTP伪造executionContext不进入服务端上下文；内部相同请求键的不同上下文冲突。既有普通对话应用创建分流不变。
