# 主对话扩展接入与使用体验更新方案

日期：2026-10-13。状态：grilling的Q1–Q5已确认，随后用户明确授权“开始修改代码”，本轮已实现并验证主要流程。以下保留业务决策；最终实现取舍和验收边界见本文补充及 验收记录（本地资料，未随源码发布）。

## 实现取舍（2026-10-13）

在已授权的更新范围内，按现有行为和本轮建议采用：个人Skill/Tool合计最多8项；仅本轮有效，发送失败恢复所选项；版本锁继续跨轮生效，但不自动沿用文件授权。Application单选，和Skill/Tool互斥，避免暗示应用内部会执行这些扩展。不可用个人项目显示状态但不可选择，公共能力仍在扩展页面先复制、验证和启用。多个合理候选由模型先澄清，不新增自动别名绑定。选择器分页加载个人列表并按名称/用途筛选；内置能力继续由主对话自动使用及既有扩展入口提供。

这些细节是实现取舍，不倒写为Q1–Q5逐项确认。选择不跨刷新持久化；支持同一页面内失败保留，不宣称扩展选择具有完整草稿恢复能力。官方使用指南按完整manifest匹配，未引入新包字段；无匹配时明确缺少样例。

所属模块：能力库；协作模块：工作台、应用平台。维护负责人：待分配。

## 背景与目标

用户实际使用时遇到两个问题：不知道扩展中的十进制求和工具如何填写参数；直接在主对话要求使用文本总结 Skill 时，助手只知道旧财经技能目录，无法发现个人扩展，且在用户要求“找不到就停止”的情况下仍自行总结。

已核对的代码原因、现行操作及原回归条件见 [问题定位与修复设计](对话发现与使用示例修复设计.md)。该文保留定位依据；本方案作为本次扩大后的更新范围及业务决策入口。未实现的目标不能当作当前功能说明。

本次要让用户看得懂扩展、能在主对话选择或自动发现扩展，并能确认它是否真正被使用。

## 输入框「+」交互

「+」不再只提供本地文件上传，同时提供选择 Skill、选择 Tool 和选择 Application 的入口。“本地能力”指平台内当前用户有权访问的能力库及应用列表，不要求用户查找磁盘上的技能文件。

选择列表应能让用户看见名称、用途、来源和可用状态。发送前，以可移除的标签展示所选对象，明确区分文件、Skill、Tool 和 Application。界面标签只是选择结果，不能显示为已经加载或执行成功。

文件继续沿用当前上传和当轮授权机制。选择 Skill/Tool 形成明确的本轮偏好；选择 Application 形成运行已有应用的意图。选择本身不立即执行，发起执行仍遵循发送和已有应用流程。

选择数量、跨轮保留规则，以及 Application 与 Skill/Tool 混选的规则尚未确认，见待决项；实现不能自行将它们视为已有共识。

## 主对话决策规则

| 用户情形 | 预期行为 |
| --- | --- |
| 未主动选择能力 | 在允许范围内按任务需要自动发现和使用 Skill/Tool |
| 仅选中 Skill/Tool | 优先判断这些能力能否完成任务，适用则使用；不适用时说明原因，可以使用其他可用方式 |
| 明确要求必须使用、禁止替代 | 实际使用指定能力；无法使用则说明原因，停止无法满足约束的相关任务 |
| 明确要求找不到即停止 | 找不到时只说明缺失，不继续完成原任务，不以模型自身能力替代 |
| 能力存在但不可用 | 区分未验证、未启用、验证失效等原因，不误报为不存在，不自动解除限制 |
| 主动选择 Application | 按已有应用的参数和执行流程处理，不忽略选择后自行回答 |

自动发现不是把整个能力库正文加入每次对话。先提供或检索名称、用途及身份信息，再按需加载 Skill 正文、参考资料和 Tool 参数定义。候选解析和执行均限定当前用户权限；不把用户导入代码注入全局内置目录。

“文本总结”可能是用途描述，实际公共样例名称是“资料摘要方法”。系统需要支持用途发现，但不能仅凭相似名称认定为同一资产。重名、多候选和明确指名的匹配策略属于待细化事项。缺失依赖仍按既有精确身份核对，不因对话检索能力而引入自动依赖替换。

主对话接入需保留历史上下文、模型选择、搜索、附件授权、停止和原内置能力。已有个人能力的显式选择流程继续可用，正常输入框入口必须覆盖验收，不能只验证独立测试入口。

## Application 使用边界

选中的已有应用应显示其用途和必要输入。参数不完整时先收集参数，不能猜测重要输入后直接执行；参数完整后进入已有应用执行规则。本次不会因加入「+」而跳过已有确认步骤。

没有主动选择应用时，现有自动分流规则维持原状。本次不将“可以自动发现 Skill/Tool”扩展解释为“可以任意自动执行应用”。应用内部消费个人扩展、临时改写应用流程及混合编排不在已确认范围内。

## 使用示例与首次使用

每个官方示例在详情里提供以下内容，用户无需阅读源码：

- 用途和适用场景、前置条件。
- 完整的输入及字段解释。
- Tool 的预期结果，或 Skill 的可人工判断的验收标准。
- 可复制的对话提问。
- 从验证到启用再到对话使用的操作步骤。

“填入验证示例”只填写表单，不自动开始验证或调用。自定义能力没有作者或维护者样例时，明确显示缺失；按 Schema 生成的输入模板不能伪装成有效业务示例，更不能虚构输出。示例应对应适用版本；结构化存储和包兼容方案需在实现前细化。

### 十进制求和

用途：对十进制字符串求和。values 是字符串数组，数值需要引号。

输入：

```json
{"values":["0.10","0.20"]}
```

预期结果：

```json
{"total":"0.30"}
```

对话提问：“请调用十进制求和工具，计算 0.10 与 0.20 的和，并报告工具返回的结果。”

首次操作：公共能力保存为个人副本 → 填入上述验证样例 → 验证通过 → 启用 → 在对话使用。当前版本仍需显式“用于对话”；本方案完成后才支持自动发现及「+」选择。是否成功调用须依据实际事件和记录，不能仅以答案为 0.30 判断。

### 资料摘要方法

测试提问：“请使用资料摘要方法，总结以下资料：本周收到客户反馈 12 条，已处理 9 条，其余 3 条等待确认。区分事实、缺失信息和结论，不补充原因。”

验收标准：正确保留 12、9、3 的含义；不编造等待原因、负责人及期限；结论以原资料为依据。结果可以采用不同表述，不要求逐字一致。

首次操作：保存个人副本 → 填入测试提问和验收标准 → 开始验证 → 人工核对并确认 → 启用 → 在对话使用。使用记录应能证明已加载对应方法，不能把模型普通总结当作 Skill 已生效。

## 真实使用反馈

对话需要区分“用户已选择”“方法已加载”“工具已调用”“应用执行中/已完成”和“不可用/失败”。选择标签不替代执行证据，发现候选不等于加载正文，模型生成答案不等于 Tool 调用成功。

没有使用用户选择的能力时说明原因；失败与不可用不能包装成成功。具体展示位置、事件字段、记录内容和折叠方式需在实现前与现有对话事件格式统一。

## 技术细化与实施顺序

1. 确认待决交互规则；按现有接口补技术设计，不先承诺不存在的新字段。

4. 补齐官方示例、表单填入及实际使用状态。
5. 完成后端、前端、浏览器与真实模型验收，记录工作区或提交版本，再同步模块进度、总状态和变更记录。
